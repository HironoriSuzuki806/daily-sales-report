## 1. 本書の目的・範囲

本書は営業日報システムの機能・業務ルールが要件どおりに動作することを確認するためのテスト観点とテストケースを定義する。対象は認証、日報（作成・編集・提出・参照・削除）、コメント、各マスタ（顧客・営業・部署）、および権限・主要な非機能とする。

---

## 2. テスト方針

テストピラミッドに沿って、ロジックは単体テスト、HTTP層・DBを含む結合は結合テスト、主要業務フローはE2Eで確認する。

| レベル | 対象 | 主な手段 | 目安 |
| --- | --- | --- | --- |
| 単体（Unit） | サービス層のビジネスルール、バリデーション | JUnit / Go test 等 | 多数・高速 |
| 結合（Integration） | APIエンドポイント、DB連携 | API自動テスト | 中程度 |
| E2E | 画面をまたぐ業務フロー（日報作成→提出→コメント） | ブラウザ自動化 | 少数・重要シナリオ |

重点的に確認するのは、業務上クリティカルな経路、エラー処理、境界値、権限境界、データ整合性とする。単純なゲッター・フレームワーク機能はテスト対象から除外する。

カバレッジ目標（目安）は、サービス層の分岐網羅80%以上、主要APIの正常・異常の双方を網羅、主要業務フローのE2E網羅とする。

## 3. テスト環境・前提

| 項目 | 内容 |
| --- | --- |
| 環境 | 専用テスト環境（本番相当のDBスキーマ） |
| 認証 | テスト用ユーザー（SALES / MANAGER / ADMIN 各1名以上） |

テストユーザー前提（例）:

| ユーザー | ロール | 所属部署 |
| --- | --- | --- |
| sales_a | SALES | 東日本営業部 |

| mgr_a | MANAGER（東日本営業部 部署長） | 東日本営業部 |
| admin | ADMIN | 管理部 |

## 13. 今後の検討事項

- 提出後の編集ロック仕様が確定したら、再提出・締め後編集のケースを追加する。
- コメントの編集・削除APIを実装する場合、対応するテストケースを追加する。
- 同時更新の競合制御（楽観ロック等）の方式確定後、TC-NFR-002 を具体化する。
- 性能目標値（応答時間・同時接続数）の確定後、TC-NFR-001 のしきい値を設定する。
